# 《跨站点跨租户跨会话 KV Cache 全局复用侧信道防护解决方案报告-Gemini》评审与 V2 对比分析

**评审对象**：`跨站点跨租户跨会话KV Cache全局复用侧信道防护解决方案报告-Gemini.md`  
**基准方案**：`跨站点跨租户跨会话KV Cache全局复用侧信道防护解决方案报告（更新版V2）.md`  
**评审日期**：2026-11-11  
**评审目的**：识别 Gemini 方案中值得吸收的部分，指出不合理、过度承诺或会引入新风险的部分，并给出 V2 的合并建议

---

## 0. 结论摘要

### 0.1 总体判断

Gemini 方案与 V2 **高度同构**，其核心结构基本是 V2 的压缩重述：

- G/A/P 三池；
- 原子块匹配；
- 来源/ACL 自动作用域；
- 前缀血缘交集；
- 发布/授权时预热；
- 无命中标识与旁路治理。

它真正新增的内容主要是：

1. **分池动态配额与跨池冷热置换保护**；
2. 把 V2 已有的 `parent_commitment` 重新命名为“带锚点承诺的原子块”；
3. 增加一节“外部黑盒特征”；
4. 增加一节“专利侵权举证方法”；
5. 用更短的篇幅强调凭证预计算（V2 已有 CacheViewTicket）。

因此，**“最终完整增强版”这一命名并不准确**：它更像 V2 的精简导读 + 少量运维增强 + 少量专利/取证表述，而不是一个在安全机制上全面升级的新方案。

### 0.2 可借鉴 / 不合理一览

| 类别 | 内容 | 判断 |
|---|---|---|
| 可借鉴 | 分池动态配额、跨池置换保护 | 可作为可用性和驱逐侧信道的运维增强，但不能当作隐私主防线 |
| 可借鉴 | 把 `parent_commitment` 明确为“上下文/位置完整性锚点” | 有价值，但必须限定为正确性/完整性机制，而不是保密机制 |
| 可借鉴 | “外部黑盒特征”用于红队验证和方案识别 | 可作为测试观测项，但不能作为产品对外特征或安全承诺 |
| 可借鉴 | 凭证预计算的性能描述 | 已有，可保留，但必须补 TTL 与撤销机制 |
| 不合理 | “彻底切断时序侧信道盲打” | 绝对化，忽略块成员关系、块尾预测、授权组内部活动等残余风险 |
| 不合理 | 把“响应时延量子化跳跃”当外部特征 | 它本身就是一个可观测侧信道，与“命中状态不出接口”矛盾 |
| 不合理 | “错误响应相近时延” | 未说明如何实现；接近时延≠统一时延，可能重新引入延迟注入 |
| 不合理 | 把父块承诺当成防攻击机制 | 父块承诺主要防错误拼接/投毒，不能防止知道完整上下文的成员探测 |
| 不合理 | 动态配额被写成安全增强 | 它主要解决资源挤占和驱逐，不是抗侧信道机制 |
| 不合理 | 专利举证方法作为方案章节 | 黑盒时序、源码审计、流量抓包都不能直接证明专利侵权；应由专利律师和权利要求对照表处理 |
| 不合理 | 缺失 V2 中的残余风险和边界 | 导致报告过度自信，容易在评审时被反问 |
| 不合理 | 省略跨站点、撤销、请求流程、验证指标等工程细节 | 不能自称“完整版” |

**结论**：V2 应作为主方案；从 Gemini 选择性吸收“动态配额”和“父块承诺的完整性解释”，但拒绝其绝对化安全结论、黑盒特征叙事和直接侵权举证表述。

## 1. Gemini 方案与 V2 的关系

### 1.1 结构对照

| V2 章节 | Gemini 对应内容 | 关系 |

| G/A/P 三池 | §2.1 | 直接继承 |

| 内容定义分块 | §3.1 | 继承 |

| 无命中标识、旁路治理 | §5.1 | 继承并简化 |
| CacheViewTicket | §2.2 | V2 §9.4 已有，Gemini 强调预计算 |
| 发布/授权预热 | 摘要与 §2.1 提及 | 继承但未展开 |
| 跨站点策略 | 基本省略 | 缺失 |

| 实施与验证 | 未保留 | 缺失 |
| 专利举证 | §6 | 新增，但不属于技术方案主体 |

### 1.2 什么才是真正新增

逐条判断：

1. **分池动态配额**  
   这是 Gemini 相对 V2 最实质的新增。V2 §13.5 只提到“公共池与私有池采用独立容量配额，减少驱逐侧信道”，Gemini 将其扩展为“动态配额、跨池冷热置换保护”。这有工程价值，但需要进一步规约。

2. **“带锚点承诺的原子块”**  
   V2 §7.2 的块键公式已经是：

   ```text
   块键 = Hash/HMAC(scope || model_manifest || block_tokens || parent_commitment)
   ```

   Gemini 的公式：

   ```text
   BlockKey = HMAC(ScopeKey, model_manifest || block_tokens || parent_commitment)
   ```

   除写法外没有引入新的保密机制。父块承诺的作用是绑定上下文链，防止块被错误拼接到不同前缀，属于**完整性/正确性**，不是**机密性**。

3. **外部黑盒特征**  
   新增，但其内容本身与安全目标冲突，详见第 3 节。

4. **专利侵权举证**  
   新增，但技术证据和法律证据之间存在较大鸿沟，不能直接作为方案结论。

5. **凭证预计算**  
   V2 已有 `CacheViewTicket` 和本地策略版本校验。Gemini 只是把它压缩成一句增强描述，没有新增安全属性。

## 2. 值得借鉴的部分

### 2.1 借鉴一：分池动态配额与跨池置换保护

**Gemini 主张**：

> 物理缓存层为 G、A、P 三池设定动态显存配额比例，并引入跨池冷热置换保护，防止私有洪峰挤压公共资产缓存。

**为什么值得借鉴**：

- 三池逻辑隔离后，物理上仍共享内存/显存。如果私有请求洪峰把公共 G 池或授权 A 池挤出，会导致：
  - 公共内容命中率下降；
  - 授权共享内容反复回源；
  - 攻击者可以通过驱逐行为观察共享资源状态；
  - 正常用户体验波动。
- 固定或动态配额可以保证 G/A 的最低驻留能力，减少“私有流量挤压公共资产”的副作用。
- 它属于**资源隔离与可用性增强**，与缓存作用域隔离是互补关系。

**但必须补充的约束**：

1. **配额不是隐私主防线**  
   配额只能降低资源竞争和驱逐影响，不能阻止攻击者查询受害者私有池；必须与 G/A/P 逻辑隔离同时使用。
2. **配额算法需要明确**  
   - G 池最低保留比例；
   - A 池按授权组或站点最低保留；
   - P 池按用户/租户上限；
   - 配额调整的时间尺度、滞回和抢占规则；
   - 配额变化不能导致公共命中率出现可被外部观测的剧烈抖动。
3. **跨池置换必须有边界**  
   跨池“冷热置换保护”不能把 P 池的条目置换进 G/A 池，也不能让 G/A 的回收影响 P 池索引可见性。
4. **容量指标不应对外暴露**  
   配额执行状态、驱逐次数、池占用率应只对内部运维和审计可见。

**建议并入 V2**：放在“跨站点部署/旁路治理”中，标题写成“配额与驱逐隔离”，并明确“不是隐私安全机制，而是可用性与驱逐侧信道缓释”。

### 2.2 借鉴二：把父块承诺解释为完整性/上下文锚点

**Gemini 主张**：

> 块键引入父块承诺，使攻击者即使猜对中间段落，由于缺乏正确的上下文父块链条，也无法将其拼接到全局缓存目录中。

**可借鉴的点**：

- `parent_commitment` 可以防止：
  - 不同上下文链中的块被错误拼接；
  - 跨站点传输时块被投毒或替换；
  - 依赖 DAG 中的上游缺失时错误复用下游 KV；
  - 利用块注入破坏缓存完整性。
- 对 RAG 多文档组合、Agent 工具返回拼接、跨站迁移有工程价值。

**必须纠正的点**：

1. **它不是保密机制**  
   攻击者如果已经知道父块内容，就可以计算正确的父块承诺，仍可构造完整候选链。父块承诺不能阻止“知道完整上下文后做成员探测”。
2. **它不能替代作用域隔离**  
   父块承诺只约束“块链是否对得上”，不约束“谁有权查询”。真正的跨租户防护仍靠 G/A/P 池可见性。
3. **它会限制复用**  
   同一文档片段出现在不同父链下（不同 System Prompt、不同 RAG 组合、不同位置）会产生不同块键，降低跨场景复用。应说明这是**正确性优先**的取舍，必要时为公共内容提供可选的“位置无关块”模式。
4. **不应把它写成“抗侧信道创新”**  
   它在 V2 中已经存在；Gemini 的“增强”是表述增强，不是机制增强。

**建议并入 V2**：在 §7 原子块设计中增加一小段“完整性锚点”说明，明确：
- `parent_commitment` 用于上下文链完整性和防投毒；
- 不承担保密职责；
- 对复用范围的影响和适用场景。

### 2.3 借鉴三：外部黑盒特征可用于验证，不可作为产品特征

**Gemini 主张**：

> 响应时延的“量子化跳跃”：未凑齐完整块前保持未命中时延，凑齐后 TTFT 呈非连续块级突变式下降。

**可作为测试观测项**：

- 红队可以用“阶梯递增前缀 + TTFT 分布”验证系统是否真的采用原子块匹配；
- 可以用“跨会话加速持久性”验证 P 池是否按用户隔离；
- 可以用“越权查询错误一致”验证存在性预言机是否关闭；
- 这些属于**测试方法**，不是安全能力本身。

**不能作为产品对外特征**：

- 它本身就是一个可观测的侧信道信号；
- 如果攻击者位于 A 池授权组内，块级突变可暴露共享块的存在和访问活动；
- 如果系统把这种“量子化跳跃”当作可宣传的取证特征，等于主动保留一个时序泄露面；
- 应将其列为“残余可观测性”，只在内部测试和专利分析中使用。

**建议并入 V2**：放到验证/评估章节（如果恢复该章节）或作为红队测试项，不要写入“方案外部特征”。

### 2.4 借鉴四：凭证预计算的性能表达

**Gemini 主张**：

> 静态资产和项目级 ACL 权限血缘在会话建立时预计算并固化，请求到达时只做内存级凭证与策略版本校验。

V2 已有 `CacheViewTicket`。Gemini 的表达更简洁，可作为摘要用语。但必须补充：

- 凭证有效期；
- 撤销传播；
- 策略版本不可只靠内存校验，必须有可信撤销源；
- 长期凭证的权限漂移风险；
- 会话迁移、跨站点后的重新签发。

### 2.5 借鉴五：报告结构更紧凑

Gemini 的节标题和摘要比 V2 更短，适合汇报。可以把 V2 的“执行摘要”进一步压缩成一页版本，但不要为了紧凑牺牲边界条件。

## 3. 不合理或有风险的部分

### 3.1 风险一：“彻底切断时序侧信道盲打”是过度承诺

**Gemini 0.1 与 0.2 结论**：

> 彻底切断时序侧信道盲打。

**问题**：

V2 已明确，原子块只能把逐 Token 线性恢复变成“需要先知道几乎完整块”的稀疏成员探测，不能消灭所有泄露。Gemini 的绝对化结论忽略了以下残余：

1. 攻击者如果已知一个块前 B−1 个 Token，仍可测试最后 1 个 Token；
2. 攻击者如果从其他渠道获得完整块，仍可测试成员关系；
3. 授权组内部成员仍可能观测共享内容的活动痕迹；
4. 公共内容本身的缓存状态可被观测，只是没有私有内容价值；
5. 错误公共登记/错误 ACL 会让私有内容进入可查询池；
6. 同账号被控、内部管理员、物理侧信道不在方案范围；
7. 目录或节点被攻破可能暴露作用域索引；
8. “块级突变”本身是可观测信号。

**正确表述**：

> 在攻击者不拥有受害者缓存池访问权限的前提下，跨租户/跨用户逐 Token 时序恢复被阻断；共享池的完整原子块匹配将成员探测限制为“需要已知完整块”的稀疏场景。

**建议**：把“彻底”改为“阻断主要逐 Token 恢复路径”或“将泄露界定在可度量范围内”。

### 3.2 风险二：把“量子化跳跃”当外部特征，和“命中状态不出接口”自相矛盾

Gemini §5.1 说：

> 对外接口不含 cache_hit、hit_tokens、X-Cache-Node 等指标。

但 §5.2 又说：

> 响应时延的“量子化跳跃”是系统外部特征。

**问题**：

- 没有显式字段不等于没有侧信道；
- 块级 TTFT 突变本身可以被攻击者测量；
- 如果攻击者在 A 池内，可以用该突变推断共享块何时进入/离开缓存；
- 如果块边界可推断，还可做块成员探测；
- “无命中标识”只关闭了显式字段，没有关闭时序信道。

**正确处理**：

- 把它作为**残余风险**记录；
- 在红队验证中主动测量；
- 不要把它当成安全卖点或对外宣传特征；
- 如果确实要减少这种可观测性，可在 A 池内部调度上做“块级释放平滑”（但这会增加复杂度，且不能声称彻底消除）。

### 3.3 风险三：“错误响应相近时延”没有给出可执行实现

Gemini §5.1 说：

> 对无权访问、资源不存在、未命中的请求，采用统一结构和相近时延的响应。

**问题**：

- “相近”不是“一致”，仍是可测量差异；
- 如果通过人为增加延迟来实现，等于引入局部延迟注入，和“零增加延迟”目标矛盾；
- 如果不增加延迟，只是统一错误结构，不能保证时序一致；
- 共享资源竞争、异常路径开销都可能让错误时延不同；
- 授权判断应在查询前完成，避免“先查后判”产生 oracle。

**正确处理**：

1. 先鉴权，再查询；未授权请求不进入目录；
2. 错误结构和状态码统一；
3. 不承诺错误时延完全一致，只承诺不提供细粒度存在性差异；
4. 如确需时序一致，可对错误路径采用固定处理路径，而不是全局延迟。

### 3.4 风险四：父块承诺被误写成抗攻击机制

Gemini §3.1：

> 即使攻击者猜对了某中间段落，由于缺乏正确的上下文父块链条，也无法将其拼接到全局缓存目录中。

**问题**：

- “拼接块”是完整性问题，不是保密性问题；
- 攻击者通常构造完整候选前缀，不需要“拼接”；
- 若攻击者知道父链，可以计算承诺；
- `parent_commitment` 若参与 HMAC，且 ScopeKey 对授权成员可见，则授权成员可以自行计算块键，不能阻止授权组内部的成员探测；
- 该机制主要防止：
  - 块被错误拼接；
  - 跨上下文污染；
  - 依赖 DAG 缺失下游错误复用；
  - 跨站迁移投毒。
- 它不是“阻断逐 Token 侧信道”的新机制。

**建议**：明确写成“完整性锚点/上下文依赖校验”，不要写“抗侧信道创新”；如果作为专利点，应落到“块链完整性校验 + 作用域隔离”的组合，而不是单独父块承诺。

### 3.5 风险五：动态配额不是隐私机制，且缺少算法细节

Gemini §2.2：

> 分池动态配额、跨池冷热置换保护，防止私有洪峰挤压公共资产缓存。

**问题**：

- 这只解决资源挤占和驱逐，不解决“攻击者查询受害者缓存”；
- 动态调整可能引发新的可观测抖动；
- 若 P 池洪峰导致 G/A 池驱逐，反而增加缓存状态变化；
- 没有给出配额最小值、更新周期、优先级、抢占、失败回退、与跨站复制的关系；
- 如果“跨池置换保护”允许块在池间移动，可能破坏作用域隔离。

**建议**：

- 只作为运维/容量章节；
- 明确 G/A 最小保留、P 上限、池间不迁移逻辑条目；
- 与安全章节分离，避免读者误以为配额是抗侧信道主防线。

### 3.6 风险六：凭证预计算缺少撤销与 TTL

Gemini 声称请求时只做内存级凭证校验。若凭证长期固化：

- ACL 被撤销后旧凭证仍有效；
- 用户被移出项目后仍可访问 A 池；
- 策略版本更新不能立即传播；
- 跨站点迁移可能携带旧权限。

**必须补充**：

- `CacheViewTicket` 有效期；
- 撤销列表/策略版本源；
- 会话建立、站点切换、ACL 变更时重新签发；
- 旧条目隔离；
- “内存级校验”不等于“无需撤销传播”。

### 3.7 风险七：专利侵权举证方法缺乏技术/法律可靠性

Gemini §6 提出：

1. 行为学探测与时序分析：通过块级突变证明采用类似原子块；
2. 源码/组件审计：发现 `pool_type`、`effective_scope`、`policy_epoch`、CDC 类/函数即为直接侵权证据；
3. 流量抓包：观察跨站 KV 拉取是否携带作用域凭证。

**技术问题**：

- TTFT 受负载、模型、网络、批处理影响，块级突变不是唯一解释；需要严格控制变量、多信号交叉验证；
- 黑盒行为最多证明“表现相似”，不能证明内部实现了专利权利要求中的全部技术特征；
- 源码审计、容器镜像反向工程可能受许可证、保密协议和法律法规限制；
- 跨站流量通常加密，抓包看不到作用域凭证；
- 内部类名/函数名不是权利要求特征，不能直接等同侵权；
- 专利侵权判断需要**权利要求对照表（claim chart）**，由专利律师/代理人完成。

**建议**：

- 将 §6 从技术方案主体移出；
- 改为“技术验证与取证辅助假设”，明确局限；
- 正式的专利布局/侵权分析由专利律师处理；
- 不要把“行为相似”写成“直接侵权证据”。

### 3.8 风险八：省略了 V2 中最必要的边界与工程细节

Gemini 自称“最终完整增强版”，但缺少：

- 跨站点部署与路由策略；
- 授权撤销与 policy_epoch 失效；
- 请求处理流程与伪代码；
- 原子块参数与复用损失；
- 性能开销与复用评估；
- 红队测试与验证指标；
- 残余风险章节；
- 同租户不同用户、授权恶意成员、目录泄露等威胁；
- 公共内容误登记风险；
- 内部管理员/节点被攻破边界。

因此它不能替代 V2，只能作为 V2 的汇报摘要或补充运维说明。

## 5. 建议如何合并到 V2

### 5.1 应吸收的部分

1. **动态配额与驱逐隔离**
   - 位置：运维/容量/旁路治理；
   - 内容：G/A/P 最低保留、P 上限、池间不迁移、配额变更滞回、内部指标不对外；
   - 定位：可用性 + 驱逐侧信道缓释，不是隐私主防线。

2. **父块承诺的完整性说明**
   - 位置：§7 原子块设计；
   - 内容：`parent_commitment` 用于上下文链完整性、防投毒、跨站迁移校验；
   - 明确：不承担保密职责，不替代作用域隔离；
   - 明确：会限制跨父链复用，需按业务权衡。

3. **凭证预计算的性能描述**
   - 保留 V2 的 CacheViewTicket；
   - 增加 TTL、撤销传播、跨站重签；
   - 不要写成“只做内存校验即可”。

4. **红队测试观测项**
   - “块级突变”“跨会话加速持久性”“错误一致性”作为测试信号；
   - 不作为产品对外特征；
   - 测试需控制负载、模型、网络、批次变量。

5. **摘要结构**
   - 可以借鉴 Gemini 更简洁的摘要，但保留 V2 的安全边界和取舍。

### 5.2 不应吸收的部分

1. **“彻底切断”及绝对化结论**；
2. **把“量子化跳跃”作为外部特征/卖点**；
3. **“错误响应相近时延”作为已完成机制**（没有实现路径）；
4. **把父块承诺包装成抗侧信道新机制**；
5. **把动态配额当隐私主防线**；
6. **把黑盒时序/源码审计/流量抓包作为直接侵权证据**。

### 5.3 建议 V2 的新增表述（可直接引用）

> **完整性锚点说明**：原子块键包含父块承诺，用于保证块与上游上下文链、位置依赖的一致性，防止跨上下文错误拼接和投毒；该承诺属于完整性与正确性机制，不承担保密职责。跨租户/跨用户保密性由 G/A/P 作用域隔离承担；父块承诺不能阻止已知完整上下文的成员探测。

> **配额说明**：G/A/P 物理共享但配置独立容量配额，目的是避免私有流量挤压公共/授权缓存并降低驱逐带来的可用性波动；配额不是隐私隔离的替代品，池间逻辑条目不得因配额调整跨池迁移。

## 6. 最终结论

### 6.1 对 Gemini 的定位

- 可作为 V2 的**精简导读版**；
- 可吸收其**动态配额**和**父块承诺完整性解释**；
- 不宜作为 V2 的替代版本；
- 其“最终完整增强版”“彻底切断”以及“黑盒特征/专利举证”表述需要撤回或重写。

### 6.2 V2 应保持的优势

1. 明确三池与 A/B/C/D 映射；
2. 明确请求流程、缓存键、授权凭证；
3. 明确原子块的适用池、块长权衡、禁止回退；
4. 明确残余风险与安全边界；
5. 不把时序可观测性当作安全卖点；
6. 不把技术相似性当作法律侵权证据。

### 6.3 一句话总评

> Gemini 方案在结构上继承了 V2 的主线，真正新增且有价值的是“动态配额 + 父块完整性解释”；但它在安全结论上重新引入了绝对化表述，并把可观测的块级时序变化包装成“外部特征”，这与侧信道防护目标相冲突。V2 应保留为基线，选择性吸收这两点，不采纳“彻底切断”“量子化跳跃卖点”和“黑盒直接侵权举证”的写法。
