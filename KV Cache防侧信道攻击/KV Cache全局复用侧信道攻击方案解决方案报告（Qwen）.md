# 全局 KV Cache 共享下的时序侧信道防御：完整解决方案

---

## 一、核心问题回顾

在端-边-云协同的全局 KV Cache CDN 架构下，缓存命中（Hit，~10ms）与未命中（Miss，~5000ms）之间存在巨大时间差。攻击者通过逐 Token 微调 Prompt 并测量响应时间，可逐位恢复其他租户的私有前缀内容。6G 确定性网络与边缘高密度共享进一步放大了攻击精度。

**现有方案的死局**：

- 严格租户隔离 → 摧毁全局复用率
- 全局延迟注入 → 恶化合法用户体验
- API 限流 → 无法防御分布式慢速攻击

---

## 二、总体设计思想

### 核心原则：三个"绝不"

| 原则              | 含义                   |
|:--------------- |:-------------------- |
| **绝不破坏全局复用**    | 能复用尽量复用，公共内容完全开放共享   |
| **绝不恶化用户体验**    | 合法用户首字延迟（TTFT）零增加    |
| **绝不依赖用户/业务配合** | 不打标签、不识别敏感内容、不要求用户配置 |

### 破局思路：纵深防御，而非单点拦截

时序侧信道攻击成立需要三个环节：**内容暴露 → 粒度碰撞 → 时间观测**。本方案通过三个机制，分别在这三个环节上实施拦截，形成纵深防御：

```
攻击链路：  攻击者构造 Prompt → 碰撞共享池中的 KV → 观测时间差 → 推断内容

防御纵深：
  ┌─────────────────────────────────────────────────────────────┐
  │ 机制二（准入层）：控制"哪些内容进入共享池"                     │
  │ → 私有内容从源头不进入共享池，攻击者无从碰撞                  │
  ├─────────────────────────────────────────────────────────────┤
  │ 机制一（匹配层）：控制"共享池中的内容如何被匹配"               │
  │ → 块级匹配使逐 Token 微调永远无法触发命中                     │
  ├─────────────────────────────────────────────────────────────┤
  │ 机制三（调度层）：控制"对共享池的访问请求如何被调度"           │
  │ → 识别探测行为，将探测请求物理拖慢，污染攻击者样本            │
  └─────────────────────────────────────────────────────────────┘
```

---

## 三、机制一：块级哈希匹配（匹配层）

### 解决的问题

攻击者通过"每次修改 1 个 Token"进行逐位爆破，依赖的是推理引擎的 **Token 级精确匹配**（如 Radix Tree 逐 Token 遍历）。只要匹配粒度是 Token 级，攻击者就能获得清晰的"命中/未命中"反馈。

### 方案

将全局共享池的匹配粒度从 **Token 级** 提升为 **块级（Block）**：

- 前缀按固定大小（如 256 或 512 Tokens）切分为 Block
- 对每个完整 Block 计算内容哈希，仅完整 Block 进入全局目录
- 匹配时以 Block 为最小单元，**不支持块内的部分匹配**

### 效果

| 角色       | 行为                             | 结果                                                  |
|:-------- |:------------------------------ |:--------------------------------------------------- |
| **合法用户** | RAG 召回完整文档段落（通常 >> 512 Tokens） | 按 Block 直接命中，TTFT ≈ 10ms                            |
| **攻击者**  | 每次只修改 1-2 个 Token，未凑齐完整 Block  | 当前 Block 永远判定为 Miss，必须一次性盲猜对连续 512 个 Token 才能触发 Hit |

**关键点**：攻击的搜索空间从"逐 Token 线性增长"变为"$V^{512}$ 的指数空间"，逐 Token 爆破在物理粒度上被彻底瓦解。全局复用率不受任何影响。

## 四、机制二：渐进式共享准入（准入层）

### 解决的问题

机制一保护的是"已进入共享池的内容"，但更根本的问题是：**私有内容是否应该进入共享池？** 如果攻击者的目标内容根本不在共享池中，攻击就无从发起。

但简单的"租户隔离"会摧毁全局复用。因此需要一个**自动化的、渐进式的准入机制**：不依赖业务打标签，不依赖内容敏感度识别，完全由数据分布驱动。

### 方案：四态晋升状态机

```
状态 0：会话私有 (Session-Private)
   │  触发：同一租户的不同会话产生相同前缀
   ▼
状态 1：租户私有 (Tenant-Private)
   │  触发：≥2 个不同租户独立产生相同前缀 → 进入观察期
   ▼
状态 2：候选共享 (Candidate-Sharing)
   │  触发：观察期内共享度持续达标（如 ≥3 独立租户/天）
   ▼
状态 3：全局共享 (Global-Shared)
```

### 核心判据：独立来源数

$$\text{独立来源数} = |\{(\text{Tenant\_ID}, \text{Session\_ID})\}|$$

| 晋升路径     | 触发条件                       |
|:-------- |:-------------------------- |
| 状态 0 → 1 | 独立来源数 ≥ 2，且属于**同一租户的不同会话** |
| 状态 1 → 2 | 独立来源数 ≥ 2，且属于**不同租户**      |
| 状态 2 → 3 | 观察期（如 7 天）内，独立来源数持续 ≥ 阈值   |

### 冷启动兼容

- **冷启动/影子期**：完全 follow 现有实现——同一用户/租户、同一会话内的复用机制不变（vLLM/SGLang 的多轮对话、prefix cache），零改动、零风险。
- **晋升逻辑**：在控制平面"影子统计"（原报告 §2.6）基础上，增加"独立来源数"维度，复用现有的三维统计框架（周期/区域/特征）。

### 效果

| 内容类型                        | 独立来源数     | 最终状态            | 攻击者能否探测            |
|:--------------------------- |:--------- |:--------------- |:------------------ |
| 公共 System Prompt（如"你是一个助手"） | 数千租户独立产生  | 状态 3（全局共享）      | 能探测，但无隐私价值         |
| 热门 RAG 文档                   | 数百租户独立产生  | 状态 3（全局共享）      | 能探测，但属于公共知识        |
| 企业机密文档                      | 仅 1 个租户产生 | 状态 0（会话私有，即算即焚） | **不能探测——根本不在共享池中** |
| 个人对话历史                      | 仅 1 个会话产生 | 状态 0（会话私有，即算即焚） | **不能探测**           |

**关键点**：不需要识别"什么是敏感内容"，只需要看"是否被多个独立来源重复产生"。公共性由数据分布自动判定，私有内容自然被排除在共享池之外。

## 五、机制三：前缀区域异常检测与蜜罐调度（调度层）

### 解决的问题

即使有机制一和机制二，攻击者仍可能对**已进入共享池的公共内容**进行高频探测（虽然公共内容本身无隐私价值，但高频探测会挤占系统资源，且攻击者可能试图通过公共内容的访问模式推断系统状态）。更关键的是：**系统如何判断哪些请求是疑似攻击者？**

### 核心思路转变

**从"识别攻击者账号"转向"识别被攻击的前缀区域"。**

攻击者可以用多个账号、跨会话、DDoS 式分散请求，系统无法可靠识别"某个账号是攻击者"。但攻击者的**行为本质**——对同一前缀区域进行高频、微小变异的探测——是无法隐藏的。

### 方案：三步判定

**第一步：定义监控单元**

将前缀空间划分为监控单元（与机制一的 Block 对齐）：

- Block 级哈希单元
- 或 LSH 语义桶
- 或前缀树的某个深度节点

**第二步：统计四维访问特征**

对每个监控单元，在滑动时间窗口（如 5 分钟）内统计：

| 特征          | 定义                       | 攻击者特征                 | 合法用户特征            |
|:----------- |:------------------------ |:--------------------- |:----------------- |
| 访问次数        | 该单元被访问的总次数               | 极高                    | 中等                |
| 独立来源数       | 不同的（租户×会话）数量             | 可能高（多账号）或低            | 通常与访问次数成正比        |
| **微小变异聚集度** | 请求两两相似度 ∈ [0.9, 1.0) 的比例 | **极高**（每次改 1-2 Token） | 极低（要么完全不同，要么完全相同） |
| 时间集中度       | 访问是否集中在短时间窗口             | 高（机器节奏）               | 低（随机分布）           |

**核心判据——微小变异聚集度**：

$$\text{微小变异聚集度} = \frac{|\{(i,j) : 0.9 \leq \text{sim}(P_i, P_j) < 1.0\}|}{|\text{总请求对}|}$$

- 攻击者：大量请求"高度相似但不完全相同" → 聚集度 > 0.7
- 合法用户：请求要么完全不同（不同问题），要么完全相同（公共模板） → 聚集度 < 0.1

**第三步：触发后的动作——区域蜜罐化**

一旦某监控单元的探测评分超过阈值：

1. **不封禁账号**（多账号封不完）
2. **标记该监控单元为"高危"**
3. 后续访问该单元的请求，**强制路由到"背景 Batch"**（包含大量真实 Miss 重算请求的 Continuous Batching）
4. 攻击者的请求被同 Batch 的重算请求**物理拖慢**到 ~5000ms
5. 合法用户的请求（不具备探测特征）仍走"快速 Batch"，享受 10ms

### 多账号攻击的应对

即使攻击者用 1000 个账号，这 1000 个账号的请求都会落在**同一个监控单元**，且呈现"微小变异聚集"。系统看到的是"某个前缀区域被大量高度相似但微小差异的请求访问"——无论来自 1 个账号还是 1000 个账号，**访问模式本身就是异常的**。

### 效果

| 角色   | 调度路径               | 体验                    |
|:---- |:------------------ |:--------------------- |
| 合法用户 | 快速 Batch（纯 Hit 请求） | TTFT ≈ 10ms，零恶化       |
| 攻击者  | 背景 Batch（混入真实重算请求） | 被物理拖慢到 ~5000ms，收集无效样本 |

**关键点**：没有浪费额外算力（背景 Batch 中的重算请求是合法用户的真实任务），没有增加合法用户延迟，没有依赖账号识别。

## 六、三机制协同：端到端工作流程

### 请求到达时的完整决策链

```
请求到达
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 机制二：准入层判定                                    │
│ 该前缀是否已在全局共享池中？                          │
│ → 是（状态 3）：允许匹配，进入机制一                  │
│ → 否（状态 0/1）：仅在本租户/会话内匹配，不进入共享池  │
└──────────────────────┬──────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────┐
│ 机制一：匹配层判定                                    │
│ 请求前缀按 Block 切分，逐块哈希匹配                   │
│ → 完整 Block 命中：Hit（10ms）                       │
│ → 未凑齐完整 Block：当前 Block 判定为 Miss            │
│ → 逐 Token 微调永远无法触发块内命中                   │
└──────────────────────┬──────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────┐
│ 机制三：调度层判定                                    │
│ 该请求所属的监控单元是否被标记为"高危"？               │
│ → 否：正常路由至快速 Batch，享受真实低延迟            │
│ → 是：路由至背景 Batch，被物理拖慢                    │
└──────────────────────┬──────────────────────────────┘
                       ▼
                  返回响应
```

### 典型场景走查

**场景 A：合法用户查询热门 RAG 文档**

1. 机制二：该文档被数百租户独立产生，已晋升为状态 3（全局共享）✓
2. 机制一：用户传入完整文档段落（>512 Tokens），按 Block 直接命中 ✓
3. 机制三：该监控单元未被标记为高危，正常路由至快速 Batch ✓
4. **结果**：TTFT ≈ 10ms，极致体验

**场景 B：攻击者逐 Token 探测企业机密**

1. 机制二：该机密文档仅 1 个租户产生，停留在状态 0（会话私有），**根本不在共享池中** ✗
2. **结果**：攻击者永远触发 Miss，探测无从发起。攻击终止。

**场景 C：攻击者对公共内容发起高频探测**

1. 机制二：该内容已在共享池（状态 3）✓
2. 机制一：攻击者每次只改 1 个 Token，未凑齐完整 Block，当前 Block 永远 Miss ✗
3. 机制三：即使攻击者尝试整块碰撞，其"微小变异聚集"触发监控单元告警，后续请求被路由至背景 Batch ✗
4. **结果**：攻击者测到的永远是 ~5000ms 的 Miss，且被物理拖慢。攻击终止。

**场景 D：多账号分布式攻击**

1. 机制二：目标内容若在共享池，所有账号共享同一匹配逻辑 ✓
2. 机制一：块级匹配对所有账号一视同仁，逐 Token 爆破无效 ✗
3. 机制三：1000 个账号的请求落在同一监控单元，微小变异聚集度依然 > 0.7，触发区域蜜罐化 ✗
4. **结果**：无论多少个账号，访问模式本身就是异常的，全部被拖慢。攻击终止。

## 七、技术效果总结

| 维度            | 指标            | 说明                              |
|:------------- |:------------- |:------------------------------- |
| **全局复用率**     | ≥ 95%         | 机制二保证真正的公共内容自然晋升为全局共享           |
| **合法用户延迟**    | 零增加           | 合法用户走快速 Batch，TTFT 保持 10ms 物理极限 |
| **额外算力消耗**    | 零             | 不做影子预热，蜜罐拖慢复用真实重算请求             |
| **业务配合**      | 零             | 不打标签、不识别敏感内容、不要求用户配置            |
| **攻击者置信度**    | 30 天内无法 > 80% | 三层拦截使攻击者无法获得有效的梯度反馈             |
| **多账号/分布式攻击** | 无效            | 基于前缀区域访问模式判定，与账号数量无关            |

---

## 八、一句话总结

> 本方案通过 **"准入层控制暴露面（渐进式共享准入）+ 匹配层阻断碰撞粒度（块级哈希）+ 调度层污染观测样本（区域蜜罐化）"** 的三层纵深防御，在**不破坏全局复用率、不恶化合法用户体验、不消耗额外算力、不依赖业务配合**的前提下，彻底切断多租户时序侧信道攻击的反馈链路。
